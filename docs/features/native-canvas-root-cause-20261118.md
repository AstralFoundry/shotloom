# 画布加载慢的根因核验（2026-11-18）

诊断阶段核验线上 0.9.11 对应工作台，未修改产品代码。结论来自真实接口的网络时间线、CPU profile，以及只改变设置响应等待时间的对照实验。之后按用户要求完成的修复与部署记录见本文末尾。

## 已确认的原因

### 1. 设置读取仍挡在工程读取前面

`renderer/src/app/ReactWorkbench.tsx:177–196` 先等待 `loadAppSettings({ preferencesOnly: true })`，处理语言，再调用 `loadBoundWindowProject()`。工程和素材虽已并行，但必须等设置读完才能启动。`renderer/src/services/cloudApi.ts:21` 表明 preferencesOnly 仍请求 `/api/settings`，不复用原生侧设置缓存。

实际关键路径为：

```text
HTML → 入口/工作台脚本 → 设置 → max(工程, 素材) → 挂载画布
```

同一真实 QA 工程、桌面 Chromium 移动视口、无 CPU 限速的实测如下，单位毫秒：

| 阶段 | 冷加载 | 静态缓存命中 |
| --- | ---: | ---: |
| 导航开始到 HTML 接收完 | 4216 | 469 |
| HTML 接收完到开始读设置，含模块加载/执行 | 3607 | 368 |
| 设置读取及应用 | 6947 | 1372 |
| 工程与素材并行读取及应用 | 2080 | 1363 |
| 工程就绪到 DOM 挂载后的双帧回调 | 64 | 19 |
| 总计 | 16913 | 3590 |

这是单次诊断样本，不是安卓耗时分位数；双帧回调用于近似页面可呈现时机，不等同于真机物理屏幕首次呈现。

因果验证：导航前以真实 QA 会话读取真实设置，放入探针内存，仅将该次导航的 `/api/settings` 响应替换为已取得的数据；其他接口保持真实。

- 不加等待：设置阶段约 1 ms，工程在 570 ms 开始，画布双帧回调 2721 ms。
- 对同一替换响应加 2000 ms 等待：设置阶段 2003 ms，工程在 3646 ms 开始，双帧回调 5292 ms。
- 设置阶段的新增等待会完整推迟工程开始。总耗时差不能全部归于这一变量，两次导航及工程接口本身也存在网络波动。

探针不是产品缓存实现，不能将 2721 ms 宣称为已修复后的上线效果。

### 2. 每个数据接口内部还有串行 Supabase HTTP 往返

在应用服务器上另启临时容器，运行当前生产镜像的真实 `domainApp` 路由、鉴权和 Supabase 读取，未改动线上进程。设置响应仅 268 字节。

| 样本 | 会话/用户读取 | 设置读取 | 路由总耗时 |
| --- | ---: | ---: | ---: |
| 首次 | 749 | 301 | 1069 |
| 连接复用后 1 | 244 | 207 | 455 |
| 连接复用后 2 | 229 | 242 | 482 |
| 连接复用后 3 | 215 | 212 | 429 |

单位毫秒。探针的 fetch 耗时包含 HTTP 请求和响应体读取，不能当作 SQL 执行时间。

代码对应：`server/src/auth.ts:85–115` 的 `requireAuth` 等待 `loadSession()` 后再进入路由；`server/src/domain.ts` 设置路由调用 `server/src/lib/store.ts:151` 的 `loadSettings()`。会话与用户已在同一个查询中读取，但每个接口仍会查一次会话，随后再查业务数据。

同主机通过公开域名访问生产 `/api/settings` 的四次完整耗时为 641、455、512、602 ms。远端浏览器实测的设置、工程和素材请求更慢，说明用户侧网络还会增加等待。没有同一请求的端到端分布式追踪，不能精确相减，也不能把远端全部等待归为数据库慢。

### 3. 冷加载叠加了连接建立和两批模块加载

冷加载 navigation timing：DNS 17 ms；连接建立（含 TLS）2161 ms；requestStart 到 responseStart 2037 ms；HTML 传输不足 1 ms。连接建立时间不等同于物理网络 RTT，可能包含代理或协商等待。

入口和 React 脚本在约 4224 ms 发起，renderer 在 6608 ms 启动；工作台及其他依赖完成后约 7823 ms 才开始设置请求。静态缓存命中后 renderer 在 523 ms 启动，设置请求在 836 ms 启动。

`server/src/lib/workspacePreload.ts` 的预热页只 fetch 静态文件和写入 cookie，不运行工作台初始化、不获取设置/工程，也不预先挂载实际工程画布。`mobile/native/src/App.tsx:269–295` 还设置了 15 秒预热上限，cookie ready 可以早于静态预热完成。因而 cookie 可复用不代表实际工作台已准备好。此次浏览器冷样本未执行原生预热，不能据此认定安卓预热失效或必然耗时相同。

## 本次没有证实的猜测

- **重复登录检查挡住画布**：这几次有效会话追踪中 `/api/auth/me` 与启动并行；设置缓存实验中，登录检查尚未结束，工程请求已经发出。因此它不是本次加载关键路径上的串行门槛。各数据接口自己的服务端鉴权仍有成本。
- **画布渲染本身耗时几秒**：缓存命中样本没有 long task；冷样本只记录到一个 60 ms long task，CPU profile 大部分时间为空闲。此结论只适用于本次空 QA 工程及桌面 Chromium，不能覆盖安卓大工程。
- **返回同一画布必然重新登录/重新下载**：现有原生代码保留 WebView，active 变化不在 document effect 依赖中；这属于代码路径证据。此前 Android UiAutomation 计时包含同步输入和无障碍树查询，尚无同轮 WebView 时间线区分其开销，返回慢的设备端原因仍未定论。
- **数据库缺索引**：没有 EXPLAIN 或服务端 SQL 执行时间证据；HTTP 查询 200 多毫秒不能证明缺索引。
- **服务器未更新**：本次请求实际命中了 0.9.11 发布后的前端标记和生产镜像中的合并会话读取实现，不能用“服务没重载”解释这些已追踪到的等待。

## 对应的修复顺序

1. 在鉴权和账号绑定边界内，将设置与工程/素材的网络读取重叠。界面应用设置、权限和语言仍需有序；不能直接让旧设置或错误账号数据进入可交互画布。
2. 将原生端已经取得的设置、工程读取结果用于安全预取，或让实际工程 WebView 提前初始化。仅缓存静态文件无法消除两轮业务接口等待。
3. 减少启动所需 Supabase 远程往返。按真实请求跟踪结果决定启动聚合、数据缓存或部署连接调整；鉴权撤销与用户隔离必须保留，不能用长期 session 缓存掩盖问题。
4. 对安卓返回画布单独采集 document timeOrigin、reveal/visible 标记，以及同步输入/无障碍查询耗时。先区分页面重载、WebView 恢复和测试工具等待，再决定是否改原生挂载策略。

## 复核材料

- `output/canvas-root-probe.mjs`：真实在线路径的 CDP 探针；可设 `PROBE_MAX_MS=3000`，原始热样本报 `Canvas frame 3590ms exceeds 3000ms`。真实在线延迟有波动，阈值用于定位，本身不是稳定的 CI 性能预算。
- `output/canvas-root-cause/baseline.json`、`baseline-warm.json`：未替换接口的网络与页面标记。
- `output/canvas-root-cause/settings-cache-warm.json`、`settings-delay-warm.json`：设置等待变量对照。
- 同目录 `*-cpu.json`：对应 CPU profile。
- `output/canvas-server-root-probe.mjs`、`output/canvas-root-cause/server-settings.json`：生产镜像分阶段核验。

这些 output 文件为诊断产物，可能不受 Git 跟踪；未持久化 cookie、token 或请求头。此轮使用临时 QA 数据，不触发付费生成。
