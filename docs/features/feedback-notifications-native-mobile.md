# 用户反馈／举报、站内通知与 React Native 移动端迁移

状态：开发中；用户已于 2026-11-16 确认测试边界并授权开启 Issues、发布规格与开发。跟踪 Issue：https://github.com/854771076/shotloom/issues/1（ready-for-agent）。

## Problem Statement

用户缺少统一的反馈与举报渠道，也无法在应用内持续查看处理进度和后台回复。现有通知主要是临时 Toast 和消息弹窗，不能承载可追溯的消息记录。

移动端目前通过 Tauri 加载云端页面，需要改善导航、输入、返回手势和生命周期处理，使主要操作更贴近原生体验。

## Solution

3. 提供简单的反馈／举报表单、个人记录和后台回复。
4. 建立持久化站内通知，打通后台回复与用户查看的闭环。
5. 逐步引入 React Native 原生界面，复用已有服务端能力，并为复杂工作区保留过渡方案。

“通知完善”暂按站内通知闭环拟定，系统推送留待后续。

## User Stories

1. 作为用户，我希望从固定入口提交反馈，以便快速报告问题。
2. 作为用户，我希望明确选择反馈或举报，以便说明提交目的。
3. 作为用户，我希望填写问题描述，以便后台理解实际情况。
4. 作为用户，我希望举报时携带可用的对象引用，以便后台定位对象。
5. 作为用户，我希望提交失败时保留已填内容，以便重试。
6. 作为用户，我希望提交成功后获得记录编号，以便后续查询。
7. 作为用户，我希望查看自己提交的记录，以便跟踪处理进度。
8. 作为用户，我希望查看后台回复和回复时间，以便了解处理结果。
9. 作为用户，我希望自己的反馈与举报仅向有权限的人开放，以便保护隐私。
10. 作为管理员，我希望查看反馈与举报列表，以便集中处理。
11. 作为管理员，我希望按类型和状态筛选，以便找到待处理事项。
12. 作为管理员，我希望查看描述和关联对象，以便判断问题。
13. 作为管理员，我希望回复用户，以便解释处理情况。
14. 作为管理员，我希望更新处理状态，以便标识进展。
15. 作为管理员，我希望保留处理操作记录，以便追溯责任。
16. 作为用户，我希望后台回复后收到站内通知，以便及时获知。
17. 作为用户，我希望看到未读数量，以便发现待查看消息。
18. 作为用户，我希望查看通知列表，以便找回之前的消息。
19. 作为用户，我希望点击通知打开对应记录，以便阅读完整上下文。
20. 作为用户，我希望标记单条或全部通知已读，以便管理未读消息。
21. 作为用户，我希望刷新或重新登录后仍能看到通知和已读状态，以便连续使用。
22. 作为用户，我希望通知目标失效时得到明确说明，以便理解无法打开的原因。
23. 作为用户，我希望同一事件重试时不重复产生通知，以便避免干扰。
24. 作为移动端用户，我希望使用符合平台习惯的导航与返回操作，以便自然切换页面。
25. 作为移动端用户，我希望键盘和安全区域不遮挡表单，以便顺畅输入。
26. 作为移动端用户，我希望切换后台再返回时恢复页面并刷新数据，以便继续操作。
27. 作为移动端用户，我希望网络中断或登录失效时保留输入并得到恢复入口，以便完成提交。
28. 作为移动端用户，我希望通知能直接打开对应详情，以便减少寻找步骤。
29. 作为移动端用户，我希望长列表滚动流畅，以便查看较多记录。
30. 作为现有用户，我希望移动端迁移后仍可访问已有工程，以便持续使用已有成果。

## Implementation Decisions

以下为开发约定；第一阶段交付情况与未验收项见 Further Notes。

- 反馈与举报共用提交与处理模块，以类型区分。首版提供类型、描述及可选的对象引用；从对象入口发起时自动带入真实引用。
- 处理流程采用待处理、处理中、已处理状态；回复保存作者与时间。回复成功持久化后才向用户显示成功。
- 后台扩展现有管理界面，复用已有管理员身份和权限边界，服务端校验每次管理操作。
- 普通用户只能访问自己的提交、回复和通知；关联对象继续执行原有访问权限。
- 通知保存接收人、事件标识、摘要、目标引用、创建时间和已读时间。回复与通知之间建立可靠关联，失败可恢复，重试不重复创建。
- Toast 继续承担即时操作提示；通知中心承载持久消息。关闭 Toast 不改变通知已读状态。
- 首版通过进入页面、应用恢复前台和手动刷新获取最新数据，不预先引入推送基础设施。
- 接口提供提交、个人列表与详情、后台列表与回复、状态更新，以及通知列表、未读数和已读操作；沿用现有响应与错误约定。
- 状态管理遵守仓库领域状态与界面状态的分层约定。移动端若需要不同状态方案，应先补充架构决策，避免直接扩散第三套引擎。
- React Native 先覆盖导航、反馈表单、通知列表及详情。复用平台无关的接口契约和业务逻辑，界面使用原生组件。
- 画布、导演台和剪辑工作区采用明确的 WebView 过渡边界；不将 DOM、桌面 IPC 或桌面运行时依赖直接带入原生界面。
- 原生登录、会话恢复、退出和发布流程作为迁移验收内容，不能假定现有 WebView 登录机制可直接复用。
- 在固定设备和数据集上记录启动、页面切换、列表滚动及内存基线，再据此确定优化目标。

## Testing Decisions

- 主要测试边界：以现有服务端应用请求入口进行集成测试，覆盖“用户提交 → 管理员回复 → 用户收到通知 → 打开记录 → 标记已读”的完整链路。此边界已经用户确认。
- 验证真实外部行为，包括持久化结果、权限隔离、失败重试、重复请求和未读状态；不以源码文本匹配作为功能验收。
- 延续已有服务端安全测试的请求入口方式；持久化链路使用隔离测试数据。
- 现有通知行为测试继续覆盖 Toast 排队、去重及关闭行为，防止通知中心影响即时提示。
- 原生界面增加少量关键流程测试，覆盖表单输入、返回导航、通知跳转及前后台恢复。
- 原生手势、键盘、安全区域和性能通过 Android、iOS 真机验收；现有移动发布测试继续验证迁移期打包行为。

## Out of Scope

- 完整客服工单系统、实时聊天、自动分单和服务时限管理。
- 举报自动判罚、自动删除内容或封禁账号。
- 附件上传、匿名提交、邮件、短信及系统推送。
- 一次性将画布、三维导演台和视频编辑器全部重写为原生组件。
- 全量离线编辑和桌面架构重构。
