- 会话与用户归属合为一次 Supabase 查询；/auth/me 复用该用户结果。仍逐请求验证会话是否存在、应用归属、年龄与账号匹配，没有增加服务端会话缓存。
- Cookie 建立后即可直接打开画布；静态预热继续后台运行，完成消息另报加载数与失败项。旧包仍等待原完成消息，保持兼容。
- 嵌入式画布启动并行读取工程和素材库；并发素材库读取共同等待真实请求。引用核对和文件恢复仍在就绪前完成。

- 未修改内容的技能保存不发送请求；实际修改保留 GET→PUT 并发检查。技能和设置保存成功后回填本地缓存，并阻止旧请求覆盖新快照。
- 增加 Cookie、静态预热、偏好、工程读取、工作区就绪和显示阶段的 UserTiming 标记；未恢复已移除的诊断包功能。

## 仍需关注的启动耗时

本轮完整巡检没有证明启动和画布提速：新包恢复首页比同服务旧包慢 20.3%，首次画布慢 43.3%，返回画布慢 134.5%。这些是需要保留的反向结果；不同 CI 实例及无障碍读取带来混杂，不能直接断定产品回退，也不能用它们宣称启动优化成功。

新包首次画布 P50 为 9993ms，同服务下旧包为 6973ms；同画布返回分别为 3496ms 和 1491ms。同项目 WebView 始终保留，返回计时不能解释为重新加载了整个页面。

发布构建仍包含 main 约 1.24MB、ReactWorkbench 约 0.87MB、antd 约 0.99MB 的大块文件（未压缩）。这些体积说明启动依赖仍有拆分空间，但本轮没有采集解析、执行和硬件首帧，不能只按文件大小认定耗时占比。下一轮应先采集已加入的阶段标记，再针对实际阻塞的启动依赖做延迟加载。

同机专项未完成，现有部分观测不能排除或证实完整巡检中的回退。原生冷启动和工作区返回仍需在真实设备上分别测 JS 启动、渲染与无障碍读取开销；不能把端到端数字减去独立接口探针就当作纯渲染时间。

## 限制与保留项

- 尚未验证真实 Android 硬件、完整 OAuth 授权和真实余额/模型响应；首次画布为隔离空工程，且在浏览原生页面后打开，没有独立测刚启动便立即打开画布的场景。
- 没有把完整画布改写为原生，也没有引入 Supabase KV 或弱化撤销验证。修改过的技能仍保留 GET→PUT 检查，没有增加数据库原子的版本比较与保存。
- 新阶段标记已部署；本轮外部测量没有采集这些标记，不能据此给出分阶段实测数字。
- 各指标 N 较小，P95 多为样本最大值，不代表生产长期 P95。
- 隔离账号、会话及临时 GitHub 测试 secrets 在验收完成后清理，并验证旧凭证返回 401。
