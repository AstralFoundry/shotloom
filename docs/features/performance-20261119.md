本轮已实现：Agent 后台初始化不再阻塞画布、原生 Skill 首页预取及缓存回显、剪辑工作区按需加载。未部署服务或发布 APK。

## 测量口径

- API：Windows 经公网访问已部署服务，隔离测试账号，Native Bearer / Web Cookie 分开，每接口 5 次，计时到响应体读取完成。P95 在 N=5 时基本代表最大样本，不能视为稳定尾延迟。
- Web：本地生产构建代理到真实服务，390×844 / 1280×844 Chromium。页面导航重新建立文档，同一 context 内可复用浏览器缓存；不是原生手机测试，也不是单纯前端渲染耗时。资源从本机提供，不能代表线上冷下载。
- Android：引用 2026-11-18 的 0.9.11 既有验收，详见 [完整记录](./native-performance-0911.md)。本轮没有 adb / 真机，未制造新的 Android 提速结论。
- 测试账号没有真实模型网关授权，余额、用量、模型失败响应单列；未执行付费生成、充值下单。
- 原始计时、脚本与构建保存在本机 `output/performance-20261119/`，不包含在版本控制中。没有把测试凭证写入报告。

## 根因与已实现修改

1. **画布错误等待 Agent。** `CreationView` 原来把可见 Agent 的 `loading` 算进全屏启动状态，同时令主区域 inert。现在只等待画布自己的 ready；`HarnessChatPanel` 仍保持挂载并后台加载，项目会话逻辑保持原样。手机隐藏 Agent 时原条件已不阻塞，所以不能把它说成手机慢的唯一根因。
2. **原生 Skill 进入时才发请求，且保留挂载的页面未立即回显新缓存。** 项目首页数据到达后，用既有 NativeApi 缓存/并发合并机制静默预取 Skill；Skill 获得焦点先读取缓存，再执行既有刷新流程。不会等待预取再显示首页，失败可在真正进入页面时重试，未引入额外缓存或放宽权限。
3. **剪辑工作区的静态导入抵消了懒加载。** `ClipStudioNode` 改用 React.lazy + Suspense，沿用已有占位。生产构建确认剪辑工作区独立为 54.97 KB chunk；ReactWorkbench 从 872.89 KB 降到 819.43 KB（gzip 274.72 → 258.29 KB）。这是文件大小变化，不是整页时间的等比例变化；工程实际包含剪辑节点时仍需加载该工作区。

## 是否把画布和导演台改为原生

Skill 已是 React Native 页面，重写一次不能解决其接口等待。

画布可以重做，但需要重新实现缩放/拖拽、连线、各类媒体节点、编辑器接入、Agent 工具和保存语义，并维护原生与 Web 两条行为一致的路径。本轮已确认的请求依赖、脚本阻塞和静态导入问题都可在共享实现中解决，尚无证据支持用全量原生重写换性能。

导演台是独立 iframe 的 Three / React Three Fiber 工作区，通过 bridge 同步工程事实。转原生需要替换 DOM 交互、渲染容器和导入导出链路；也不会消除数据库和模型接口延迟。本轮没有它的独立 GPU / 首帧实测，暂不把迁移作为优化方案。建议保留原生外围页面与共享复杂工作区，先测真机首帧、交互帧时间、内存，再决定是否只替换明确受限的渲染模块。

## 剩余优化优先级

1. 普通 Web 冷启动仍串行等待 settings/account/models、全局技能/模板/资源库/最近项目，再读绑定工程；嵌入式画布已有并行路径。下一步按页面真实依赖拆开 Web 启动，保留工程引用核对、文件恢复与语言一致性检查，避免简单提前 ready 造成缺数据。此项本轮只定位，未改动。
2. 主入口约 1.24 MB、projectStore 约 854 KB、antd 约 989 KB；模块分析里双语言目录占主入口的大部分。需要单独测真机解析/执行成本，再考虑按语言或功能拆分，避免仅挪动 chunk 却增加请求瀑布。
3. 已部署哈希静态资源已有一年缓存及 gzip，不再重复加缓存头。后台预热不能代替可交互验证。
4. API 继续用服务端阶段计时定位数据库/认证/业务查询，避免全局长期缓存认证或削弱项目归属检查。余额/模型需真实授权账号另测，当前错误样本不能用于成功路径优化。
